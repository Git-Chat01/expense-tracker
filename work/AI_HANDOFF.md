# 消费轨迹系统：AI 交接与经验记忆

> 面向接手 `expense-tracker` 的 AI。最后整理：2026-08-07。
> 本记录只保留可执行的项目经验；不得在此记录真实消费数据、`localStorage` 导出、令牌、密钥或个人信息。

## 项目边界

- 项目是移动端优先的个人记账 PWA，使用原生 HTML / CSS / JavaScript。
- Git 仓库根目录是 `D:\Chat Claude Code\expense-tracker`；remote 必须为 `https://github.com/Git-Chat01/expense-tracker.git`。
- 消费数据只存在用户浏览器的 `localStorage`，无服务端副本；数据安全高于功能、样式和交付速度。
- 用户沟通、代码注释使用中文；标识符保持英文。

## 不可违反的数据安全规则

1. 不得执行或新增会清空核心数据的逻辑，例如 `localStorage.clear()`、`ExpenseDB.clearAll()`；危险的重置、批量删除必须使用应用内二次确认。
2. 消费记录、分类、预算、设置等核心数据只能通过 `ExpenseDB` / `storage.js` API 读写，不直接操作对应 `localStorage` 键。
3. 新字段兼容旧数据时，只做**读取端兜底**：不做全量迁移、回填或覆盖式重写。缺失值保持“未评估/未知”，不能猜测。
4. 任何写入失败都必须可见且可处理：检查写入返回值，不能静默吞掉失败。
5. 不得破坏既有防线：预设分类使用合并式 `syncPresetCategories`，导入前备份、严格校验与回滚逻辑必须保留。
6. 修改数据层、导入导出或批量操作前，按“会不会丢数据 → 是否走 ExpenseDB → 危险操作是否二次确认”的顺序检查；大改动前建议用户先导出备份。

## 移动端与 PWA 约束

- 独立安装的 iOS PWA 中，原生 `alert` / `confirm` / `prompt` 可能静默失效；确认类交互一律使用应用内自定义弹窗。
- 用户说“手机上使用”且实现选择受影响时，先区分独立 PWA 和浏览器场景。
- 不把桌面端滚动条检测逻辑照搬到手机：移动端通常是 overlay 滚动条，交互反馈优先由实际 `scroll` 事件驱动。
- 布局改动坚持最小作用域：不要为单个视图问题改全局滚动结构；先理清渲染调用图和嵌套滚动关系。

## 代码与测试经验

- 拆分异步函数时，新函数必须自包含，不能引用调用方局部变量；Promise 回调中的错误可能被用户感知为“点了没反应”。
- 改动保存、导入、恢复或删除流程后，必须验证数据实际写入/未写入结果，而不仅是页面未报错。
- 重命名或拆函数后，搜索旧变量名和旧函数名，清除残留引用。
- 新增和编辑表单的校验规则保持一致（分类、日期、时间、金额等）。
- 涉及数据或异步 UI 流程时，优先做浏览器实测；测试数据要隔离，严禁用清空真实用户数据来准备测试环境。

## 发布 SOP（默认执行）

1. 在仓库根目录执行 Git 操作，并先核对 `git remote -v`。
2. 推送前必须 `git fetch origin`，检查状态；若本地落后 `origin/master`，先 `git rebase origin/master`。不要在落后状态下直接推送。
3. 检查工作区与 diff，只显式暂存本次目标文件。没有本地改动时，不创建空提交或虚假版本提交。
4. **用户可见的应用代码或静态资源更新**须在同一提交同步版本信息：
   - 页脚 `#app-version`；
   - 已修改 CSS / JS 资源的 `?v=` 参数；
   - `sw.js` 的 `CACHE_NAME`；
   - `updates.json` 的 `latest` 与数组首条更新说明。
   纯部署配置、文档或仓库维护变更不虚增客户端版本号。
5. 提交前执行与改动相称的检查：至少 `git diff --check`；代码改动还要做语法或行为验证。
6. 直接推送 `master`，由 GitHub Actions 发布到 `gh-pages`。
7. 推送后同时确认自定义发布工作流与 GitHub Pages 动态工作流成功；再用无缓存请求检查 `https://expense.aivar.cc` 页脚版本，不只看分支内容。

## 部署与缓存经验

- 客户端更新必须同时考虑浏览器、CDN 与 Service Worker 缓存；页面底部版本号是最终验收信号。
- 自定义发布工作流使用项目专用并发组，不能改回通用 `pages`，以避免与 GitHub Pages 内置发布任务产生竞争。
- GitHub Pages 偶发托管运行器或服务失败时，先收集 Actions 状态与日志；确认分支内容正确后再触发安全重发，不能为了重试伪造应用版本或空提交。
- 线上验证使用带缓存破坏参数的只读请求，例如 `?verify=<commit-sha>`；普通访问可能命中旧 CDN 缓存。

## 协作方式

- 复杂或影响体验的任务：先给出涉及文件、数据影响、验证方式和替代方案的计划，等用户确认再实施。
- 用户未回答需要决定的问题，不视为默认同意；删除文件、安装依赖、修改外部服务或控制台设置前必须明确确认。
- 能自动化的检查、发布和验证应主动完成；受平台限制时说明具体阻塞点和可操作路径。
- 发现额外风险或更好方案应直接提出，但不擅自扩大改动范围。
