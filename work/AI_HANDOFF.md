# 消费轨迹系统：AI 交接与经验记忆

> 面向接手 `expense-tracker` 的 AI。最后整理：2026-08-10。
> 本记录只保留可执行的项目经验；不得在此记录真实消费数据、`localStorage` 导出、令牌、密钥或个人信息。

## 项目边界

- 项目是移动端优先的个人记账 PWA，使用原生 HTML / CSS / JavaScript。
- Git 仓库根目录是 `D:\Chat Claude Code\expense-tracker`；remote 必须为 `https://github.com/Git-Chat01/expense-tracker.git`。
- 消费数据只存在用户浏览器的 `localStorage`，无服务端副本；数据安全高于功能、样式和交付速度。
- 用户沟通、代码注释使用中文；标识符保持英文。

## 不可违反的数据安全规则

1. 不得执行或新增会清空核心数据的逻辑，例如 `localStorage.clear()`、`ExpenseDB.clearAll()`；危险的重置、批量删除必须使用应用内二次确认。
2. 消费记录、分类、预算、设置等核心数据只能通过 `ExpenseDB` / `storage.js` API 读写，不直接操作对应 `localStorage` 键。
3. 新字段兼容旧数据时，只做**读取端兜底**：不做全量迁移、回填或覆盖式重写。缺失值保持“未评估/未知”，不能猜测。
4. 任何写入失败都必须可见且可处理：检查写入返回值，不能静默吞掉失败。
5. 不得破坏既有防线：预设分类使用合并式 `syncPresetCategories`，导入前备份、严格校验与回滚逻辑必须保留。
6. 修改数据层、导入导出或批量操作前，按“会不会丢数据 → 是否走 ExpenseDB → 危险操作是否二次确认”的顺序检查；大改动前建议用户先导出备份。

## 移动端与 PWA 约束

- 独立安装的 iOS PWA 中，原生 `alert` / `confirm` / `prompt` 可能静默失效；确认类交互一律使用应用内自定义弹窗。
- 用户说“手机上使用”且实现选择受影响时，先区分独立 PWA 和浏览器场景。
- 不把桌面端滚动条检测逻辑照搬到手机：移动端通常是 overlay 滚动条，交互反馈优先由实际 `scroll` 事件驱动。
- 布局改动坚持最小作用域：不要为单个视图问题改全局滚动结构；先理清渲染调用图和嵌套滚动关系。
- 记账页的产品约定是“只有大金额区域吸顶”：日期、分类、支付方式、价值评定、地点/备注和数字键盘都属于普通文档流。`#add-numpad` 位于 `#view-add .add-container` 末尾，不得使用 `fixed` 或 `sticky`，不使用 213px 人工占位，也不因地点/备注聚焦而专门隐藏。当前 `.app-container` 只有 `min-height`，真实滚动根是 `window`；`#view-add.main-view--active` 必须保持 `overflow: visible`，避免 `.main-view` 成为“声明可滚但实际不滚”的祖先而使金额吸顶失效。改滚动结构前同时测量 `window.scrollY` 与 `#view-add.scrollTop`；若改为受限高度的内部滚动，还必须同步重做分类抽屉和切页的滚动恢复。

## 代码与测试经验

- 拆分异步函数时，新函数必须自包含，不能引用调用方局部变量；Promise 回调中的错误可能被用户感知为“点了没反应”。
- 改动保存、导入、恢复或删除流程后，必须验证数据实际写入/未写入结果，而不仅是页面未报错。
- 重命名或拆函数后，搜索旧变量名和旧函数名，清除残留引用。
- 新增和编辑表单的校验规则保持一致（分类、日期、时间、金额等）。
- 涉及数据或异步 UI 流程时，优先做浏览器实测；测试数据要隔离，严禁用清空真实用户数据来准备测试环境。
- 记账页滚动验收不看“好像固定了”，要同时测量矩形：金额区进入吸顶状态后 `top` 保持稳定，数字键盘的 `top` 应随 `window.scrollY` 等量变化，且其计算定位必须是 `static`。页面滚到底时整块键盘必须能完整停在底部导航上方，不得留下额外空洞。
- 交互词汇必须先对齐可观测行为：“固定”可能指固定在屏幕，也可能指留在页面原位。对齐时要明确说清“滚动时谁停在屏幕、谁随页面移动”，不能只根据 `fixed` / `sticky` 这类实现词义猜测。记账页同时悬浮金额和键盘会从上下夹压中间表单，这是需要主动识别的交互风险。

## 记账当下的预算影响（2026-08-09）

- 产品目标是让用户在输入金额时直接看懂“记下这笔后”的状态，不能为了分析增加任何填写、按钮、弹窗或确认步骤。提示是建议信息，预算用完或超支也绝不阻止保存。
- 提示位于唯一吸顶的大金额区内、金额数字正下方；只显示一条最重要结论，不做新卡片。金额、分类、支付方式、价值评定和数字键盘尺寸保持不变，键盘继续属于普通文档流。
- 计算必须使用“已保存账单基线 + 当前尚未保存的草稿金额”，草稿只加一次且不得提前写入。金额统一按分比较，必须准确区分剩余、刚好用完与超出一分钱，不能出现 `-0`。
- 分类预算沿分类父级上溯，并汇总该预算分类下的全部后代；当前数据通常是子分类归入一级分类预算。总预算与分类预算同时存在时，只展示风险更高、对当下更可行动的一项。
- 当前预算没有按月历史快照：只有表单日期属于当前自然月时才可显示预算剩余；补记其他月份只显示该月记下后的累计金额，绝不能拿当前预算推断过去或未来月份。未设置适用预算时降级为本月累计，不催用户设置。
- 读取失败必须隐藏提示，不能把读取异常当作零消费。`js/storage-v214.js` 中正式的 `ExpenseDB.getBudgetImpactSnapshot()` 一次性返回带 `ok` 状态的只读快照；不写入、不迁移、不回填任何数据。版本化真实路径用于绕过 CDN 旧 `storage.js`，旧路径仍保留给升级期间的旧页面使用。
- 历史账单聚合只在进入记账页、金额清空、保存/撤销、跨标签页变化或页面恢复时失效重建；每次数字按键只在内存基线上做常数时间加法，避免账单多时输入卡顿。
- 验收至少覆盖：无预算、仅总预算、仅分类预算、子分类及兄弟分类汇总、80%/95%状态、刚好用完、超出 `¥0.01`、同月昨天、跨月补记、连续保存、撤销后重算、读取失败、320/390/430px 手机视口。测试只能使用隔离浏览器数据。

## 发布 SOP（默认执行）

1. 在仓库根目录执行 Git 操作，并先核对 `git remote -v`。
2. 推送前必须 `git fetch origin`，检查状态；若本地落后 `origin/master`，先 `git rebase origin/master`。不要在落后状态下直接推送。
3. 检查工作区与 diff，只显式暂存本次目标文件。没有本地改动时，不创建空提交或虚假版本提交。
4. **用户可见的应用代码或静态资源更新**须在同一提交同步版本信息：
   - 页脚 `#app-version`；
   - 已修改 CSS / JS 的页面引用；关键修复使用新的真实文件路径，`?v=` 只能辅助浏览器缓存、不能作为 GitHub Pages CDN 换新的保证；
   - `sw.js` 的 `CACHE_NAME`；
   - `updates.json` 的 `latest` 与数组首条更新说明。
   纯部署配置、文档或仓库维护变更不虚增客户端版本号。
5. 提交前执行与改动相称的检查：至少 `git diff --check`；代码改动还要做语法或行为验证。
6. 直接推送 `master`，由 GitHub Actions 发布到 `gh-pages`。
7. 推送后同时确认自定义发布工作流与 GitHub Pages 动态工作流成功；再用无缓存请求检查 `https://expense.aivar.cc` 页脚版本，不只看分支内容。

## 部署与缓存经验

- 客户端更新必须同时考虑浏览器、CDN 与 Service Worker 缓存；页面底部版本号是最终验收信号。
- GitHub Pages CDN 会忽略查询参数作为缓存键，`add.css?v=201` 与 `?v=202` 可能命中同一旧对象；关键 CSS/JS 修复不能只递增 `?v=`，应改用新的真实文件路径（并同步 `index.html` 与 SW 预缓存），否则可能出现“页脚版本已更新但行为仍旧”的混合状态。
- `updates.json` 是旧版页面发现 waiting Worker 后也会读取的向后兼容入口，不能在当前页面里硬编码成 `updates-v当前版本.json`，否则未来更新卡会永远落后一版。发布后要核对该固定入口的响应体；CDN 最长约 600 秒的旧内容窗口无法靠查询参数消除。
- Service Worker 安装时，同源核心文件必须整批成功；Chart.js 等跨域增强资源单独容错。离线回退只查当前 `CACHE_NAME`，带查询参数的页面资源用 `ignoreSearch` 匹配，避免跨旧缓存捞到历史文件。
- `expense-tracker-release-state` 只保存 Service Worker 更新阶段，不是账单数据；`activate` 清旧缓存时必须保留它，才能区分首次安装、用户确认更新与无客户端后的自动激活。页面确认“已更新”后先可靠写入 `acknowledged`，再收起提示，写失败不能静默伪装成功。
- 自定义发布工作流使用项目专用并发组，不能改回通用 `pages`，以避免与 GitHub Pages 内置发布任务产生竞争。
- GitHub Pages 偶发托管运行器或服务失败时，先收集 Actions 状态与日志；确认分支内容正确后再触发安全重发，不能为了重试伪造应用版本或空提交。
- 线上验证不能把 `?verify=<commit-sha>` 当作已绕过 CDN 的证据；应核对实际响应体哈希，并查看 `Age` / `X-Cache`。关键修复还要确认页面请求的是本次新增的真实文件路径。

## 更新提示与手机滚动复盘（2026-08-08）

### 更新提示的产品约定

- 正常状态：首页最底部只显示不可点击的版本号。新的 Service Worker 处于 `waiting` 时，在原位置替换为“发现新版本”卡；卡片头部展开本次更新说明，详情内固定保留“继续使用当前版本”和“立即更新”。
- 不要在 `install` 阶段自动 `skipWaiting()`。只要仍有旧客户端，新 Worker 必须等待用户点击“立即更新”后才接收 `skipWaiting` 消息；用户确认更新并完成刷新后，恢复为单独版本号。
- 浏览器在所有旧客户端都关闭后可以按标准生命周期自动激活 waiting Worker。遇到这种无法保留更新前选择权的情况，下次打开在同一位置显示一次“已更新到 vX”说明，详情只保留“知道了”；确认后恢复版本号且不重复显示。首次安装不得误报为自动更新。
- 页面从后台回到前台、恢复显示或重新联网时主动检查更新，但新脚本不能反向修改仍在内存中的历史版本页面；验证首个升级跨度时要如实区分“旧页纯恢复”和“已经导航/重载并加载新脚本”。
- 改这块功能前，先把已经确认的状态、文案、入口位置和按钮行为当作验收条件逐项保留。一次迭代不能为了修复一个表现问题而删掉已确认的更新说明或选择权。

### 展开、收起与滚动

- 首页可能由 `window` / `html` / `body` 滚动，也可能在受限高度的 PWA 中由 `#view-home` 滚动；任何“把卡片滚到可见位置”的逻辑都必须兼容两种情况，内部容器到边界后的剩余距离继续交给页面根层。
- 展开详情后要等布局稳定再定位（至少双 `requestAnimationFrame`）；异步加载 `updates.json` 改变高度后，如果详情仍处于展开状态，再补一次定位。用户已经收起时，异步回调不得把页面重新拉回展开位置。
- 对齐目标是整张更新卡和操作按钮完整位于固定底部导航上方，不能只让标题可见。收起或选择继续当前版本后，页面回到紧凑卡片的合适位置；点击立即更新和 `controllerchange` 刷新前，应同时将 `window`、`documentElement`、`body`、`#view-home` 归零，避免 iOS 还原旧滚动位置。
- 这类问题优先用局部对齐逻辑解决，不要为一张卡片改变全局滚动结构、底栏高度或首页布局。

### 验证与发布

- 更新提示改动必须用隔离浏览器上下文验证，不能借用或清空真实用户的本地存储。至少用 390px 左右手机视口分别覆盖“页面滚动”和“首页内部滚动”，检查展开、收起、继续使用、立即更新及按钮未被底栏遮挡；还要覆盖“waiting 后关闭唯一客户端再打开”的已更新卡，以及首次安装不误报。保留截图或可复现的测量结果。
- “已推送”不等于“用户能看到更新”。发布后除既有 SOP 外，针对更新提示还要用无缓存请求同时核对：公网页脚版本、`sw.js` 的 `CACHE_NAME`、`updates.json` 的 `latest`/首条版本，并确认自定义发布和 GitHub Pages 两个工作流都成功。
- 手机没有更新入口时，按“远端提交与工作流 → 公网页面/CDN → 新 Worker 是否 `waiting` → 页面卡片状态”逐层排查；不要仅凭本地版本号、`git push` 成功或普通访问结果宣布发布完成。

## 协作方式

- 复杂或影响体验的任务：先给出涉及文件、数据影响、验证方式和替代方案的计划，等用户确认再实施。
- 用户未回答需要决定的问题，不视为默认同意；删除文件、安装依赖、修改外部服务或控制台设置前必须明确确认。
- 能自动化的检查、发布和验证应主动完成；受平台限制时说明具体阻塞点和可操作路径。
- 发现额外风险或更好方案应直接提出，但不擅自扩大改动范围。

## 下次任务入口：审计问题修复（2026-08-10）

- 本轮已完成只读审计与隔离浏览器流程验证，尚未修改业务代码。**下次开始工作时直接进入修复，不要重复做一轮泛化审计，也不要先做新功能或视觉调整。**
- 第一优先级是数据完整性，建议先补会失败的回归测试，再做最小热修：
  1. 修复 `storage.js` / 当前版本化存储脚本的备份回环：导入必须校验并保留账单 `necessity`（`'' | need | want | impulse`），不能在提示成功后静默丢失价值评定。
  2. 核心读取必须 fail-closed：只有键确实不存在时才能使用默认值；JSON 解析、结构或 Storage API 读取失败时，新增、同步预设分类、导出和后续写入都要中止并给出可恢复提示，不能把异常当成空数据后覆盖。
  3. 统一分类引用规则：正常 UI 删除分类、编辑父级后产生的数据，必须仍能被应用自己的备份恢复。优先考虑软删除/墓碑并在 UI 与 `ExpenseDB` 双层阻止超过两层或形成环；不能迁移、猜测或改写历史账单分类。
  4. 把新增、编辑、导入和存储入口的金额、日期、分类、支付方式、价值评定校验收口到共享领域校验器；金额与预算统一按整数分处理，阻止非有限数、三位以上小数、负预算和超出产品上限的值。
- 同批安全热修：对 `stats.js` 冲动排行中的分类名停止直接插入 `innerHTML`（至少统一转义，优先安全 DOM API），并审计所有“导入数据 → innerHTML”路径；恶意分类名必须只显示为文本，不能执行。随后将 Chart.js 改为同源固定文件，增加合适的 CSP；未完成前把第三方脚本视为可读取全部本地账本的供应链边界。
- 发布流程随后补门禁：部署前强制执行全部 JS 语法、JSON/schema、版本链、HTML/SW 资源存在性、备份完整字段 round-trip 与隔离浏览器核心流程；`master` 不能再在零检查情况下直接发布。再处理 SW 的 5xx 缓存回退、只清理 `expense-tracker-v*` 缓存、waiting Worker 真实版本握手。
- 必测回归：全部账单字段导出→导入相等、删除分类后备份可恢复、损坏 JSON 不被覆盖且不能伪装成成功备份、恶意分类名只作为文本、金额/预算边界、导入部分写失败回滚、多标签页冲突提示；浏览器数据必须隔离。
- 实施顺序固定为“回归测试 → 数据热修 → 隔离浏览器验证 → 版本化真实路径与更新说明 → 发布 SOP”。不要把 1900 行主控制器拆分、CSS 清理等大规模架构重构混进第一轮数据热修；热修稳定后再逐步提取 `ExpenseService`、`BackupService`、表单控制器和通知/弹层服务。
- 开始修复前提醒用户先导出一份现有备份；不得为修复而执行 `clearAll`、全量迁移、历史值猜测或覆盖式回填。
